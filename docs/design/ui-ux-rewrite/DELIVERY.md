状态：正式重写及后续修改的交付契约；实际代码、验证和发布分别记录，不用文档完成代替产品验收。

## 1. Demo 的用途与正式设计责任

HTML Demo 用于确认产品气质、视觉语法、交互方向以及局部可操作样例。
正式界面必须根据实际任务、内容规模、业务状态、权限和设备约束继续优化，不能以
“照着 Demo 还原了”作为完成标准。工程便利不能优先于完整、统一、可用的新体验。

必须保留已经确认的方向：清晰双轨、单一设计语言、全页面覆盖、主题扩展、统一对象操作、
自然的设置层级与状态延续。具体页面结构、密度、尺寸、动作位置、响应式展开和文案
可以在真实验证中改进；改进同时更新共用规范，不能形成页面各自的风格。

规范数值是有依据的基线。若实际内容或设备暴露问题，可以修订相应 Token 或模式并复验
所有消费者，不能仅为接近截图保留已知缺陷。触控、可访问性、数据与信任边界始终满足
仓库和领域要求，不通过设计优化绕过它们。

## 3. 正式组件库及工作台的最低标准

组件分三层维护，能力差异通过明确接口表达：

| 层 | 典型内容 | 约束 |
| --- | --- | --- |
| 主题与基础尺度 | 语义 Token、主题注册、偏好解析、排版与布局尺度 | 单一来源；不依赖消息、账号秘密或领域写入 |
| 基础交互组件 | Button、Input、Select/Combobox、Switch、Slider、Tabs、Menu、Dialog/Sheet、滚动区域、反馈 | 同一组件完成适用的状态、键盘、触屏、主题与边缘定位；不绑定某个业务请求 |
| 共用产品模式 | 会话列表、消息、Composer、附件、对象动作、设置行、保存反馈、详情及列表/内容布局 | 复用成熟的行为；通过通道和对象能力适配，不能把 P2P 与 Workspace 的存储或权限合并 |

每个正式组件都需要可查阅的用途、参数与事件、状态契约、组合约束、可访问语义、
主题/密度/设备适配、使用方与对应检查。为实际行为选择受控或非受控接口，避免用一串
无关布尔参数覆盖互斥场景。业务模式不为了通用化而抹平发送、授权和保存的真实差异。

工作台必须直接导入正式应用使用的同一份组件源码。应用修复组件后，工作台与检查同时
获得修复；禁止为展示另外复制一份更漂亮但行为不同的组件。测试数据采用符合真实协议
结构的合成或经许可脱敏数据，不访问生产账号，也不包含秘密或真实聊天内容。

组件样例需要覆盖实际适用的长中文/连续字符、图标与文字组合、等待/失败/禁用、不同
选中态、键盘和触控、多主题与窗口宽度。复杂模式提供可控的异步、重试及对象变化场景。
原型中的模拟保存可供讲解，工作台里的模拟必须和真实请求适配层有明确边界；最终由
产品集成检查证明真实行为。工作台不作为面向普通用户的新功能随意加入主导航。

## 4. 架构文档必须随实现落定

[IMPLEMENTATION](IMPLEMENTATION.md) 先记录目标，再补上实际模块、导出接口、依赖方向
与代码链接。不要只交付一张与实际代码不一致的理想分层图。架构至少说明：

- 页面如何组合组件和领域适配，`App` 保留什么，组件不能跨越什么边界。
- 当前对象、路由、返回栈、阅读位置和草稿分别由谁持有，退出、重连、撤权后如何处理。
- 服务端数据、乐观显示、请求代际、幂等和回放如何协调，主题切换为什么不会重建编辑器。
- 浮层、Portal、焦点、右键/长按和移动返回的共同机制，不能每页各自拦截事件。
- 主题与偏好的正式来源、保存范围、版本迁移、缺失或无效数据的回退。
- 组件检查、工作台模拟与真实 Go 服务验收各证明什么，不能用一种证据替代另一种。

影响依赖、公共接口、持久化或架构边界的决策记录背景、备选方案、取舍、风险、迁移与
回退，遵循 [架构要求](../../development/ARCHITECTURE.md)。小范围局部取舍记在变更说明，
不要求每个间距调整建立独立文档。P2P/Workspace 的领域契约与现有 Go 能力归属持续优先。

## 5. 每个页面族的设计与验证循环

1. **复核现状与任务。** 从实际入口、角色、接口及已有回归找到要完成的任务，关联覆盖 ID。
2. **建立真实约束。** 用合成数据覆盖实际内容长度、数量、状态、权限、网络与设备差异。
3. **完成正式方案。** 依据统一设计系统重新组织信息、动作和布局，说明复用与新增组件。
4. **进入实际应用。** 用真实组件和领域适配实现，不复制报告壳层或模拟业务逻辑。
5. **操作、观察、完善。** 实际走通任务，检查焦点、返回、滚动、输入和性能；发现问题先修复。
6. **更新共同依据。** 同步规范、工作台、架构和必要回归，补充证据后才将覆盖项标为已验证。

经过真实检查仍合适的部分可以沿用；记录适用依据，不为了制造差异而强行改造。

不要求先把所有页面画成静态稿才开始实现。先用有代表性的 P2P、Workspace 和复杂设置
验证基础体系，再覆盖其余页面；内部迭代允许，最终上线仍是完整、唯一的新设计语言。
对话题、表情、Bot、通知、空间管理等复杂页面，不能因为 Demo 未画完整就删掉能力。

每个页面族在实施变更说明或对应工作记录里至少提供以下信息，无须为每个控件单独建文档：

| 记录项 | 应能回答的问题 |
| --- | --- |
| 目标与映射 | 完成什么真实任务，对应哪些 COVERAGE ID、入口、角色与能力？ |
| 约束与调整 | Demo 哪些部分沿用，哪些调整了，触发调整的内容/状态/设备证据是什么？ |
| 复用与边界 | 使用哪些正式组件，业务状态由谁持有，是否补充或改变了共用接口？ |
| 验证与缺口 | 在什么版本、窗口、浏览器、数据和网络条件下实际做过什么，哪里仍未验证？ |
| 同步与完成 | 哪些规范、样例、测试和迁移说明已同步，哪些问题仍需解决？ |

常规的留白、排版、组件状态、响应式和操作可达性优化可按已确认方向自主推进并记录。
改变产品定位、通道隐私、既有权限、数据范围或新增领域能力时，遵循既有领域和授权流程，
不能将其包装为视觉优化。也不能以继续设计为由任意更换用户已确认的品牌语言。

## 6. 禁止直接搬用的 Demo 假设

| Demo 的简化 | 正式交付必须做的工作 |
| --- | --- |
| 报告封面、目录、固定高度的应用画框 | 依据窗口与内容计算实际布局；验证软键盘、安全区、分屏、长列表和编辑器，不搬报告容器或展示字号 |
| 少量样例导航与短会话 | 以完整目标导航和覆盖账本为准，承接话题、文件、成员与低频工具；内容密集时重新组织层级 |
| “自己的消息”决定可用动作 | 使用实际对象能力和最新状态；执行仍由服务端授权，保留常驻上限、撤回条件和撤权处理 |
| 定时器完成保存和内存状态 | 接入真实请求、失败、并发、较早响应、换号和部分成功；取消不能提前执行业务动作 |
| 浏览器可定制下拉与系统回退 | 核对正式浏览器矩阵，提供一致、可访问的 Select/Combobox/Sheet 适配；不能把 Chromium 演示当成全平台通过 |
| 少量消息下的平滑滚动和漂亮截图 | 使用记录规模的合成长会话、多附件和频繁状态变化，测量输入、滚动、主题切换、内存及加载表现 |
| 页内全局变量、字符串模板和跨页面 CSS 选择器 | 在现有 React/TypeScript 架构下实现有边界的状态与组件，验证 Strict Mode、清理及兼容；不将原型脚本引入生产入口 |

可以复用经过校验的语义 Token、品牌资产、许可清晰的图标和设计规则；任何复用都要进入
正式组件契约与验证。禁止将整页 HTML 包进正式页面、整体搬入 Demo CSS/脚本、保留假的
请求成功，或为了视觉相似删除真实状态处理。业务文案不能残留报告说明与样例承诺。

## 7. 完成判定

正式交付需要同时具备页面覆盖、实际组件与工作台、符合代码的架构文档、设计调整记录、
产品任务验证和维护/发布资料。[ACCEPTANCE](ACCEPTANCE.md) 给出具体矩阵和真实门禁。
性能记录使用可复现的设备/浏览器、构建版本和数据规模，比较优化前后结果；先测基线，
再确定适用门槛，不凭原型帧率或工具启动声称达标。

为覆盖账本维护统一的交付证据索引，可按页面族集中记录并映射所有关联 ID：正式组件
与工作台入口、实际架构/设计调整记录、提交或构建版本、测试命令、环境与数据规模、
结果、截图或测试记录、未验证范围。索引链接实际产物，不复制多份容易漂移的验收表。
原型通过、组件通过、真实服务通过与真机通过分别标注，不能合并为一个含糊的“完成”。

验收比较的是任务完成、完整性、一致性、可用性与约束是否满足，不要求正式页面逐像素
复刻 Demo。视觉快照以验证后的正式组件和产品状态建立；更新快照需要解释实际变化，
不能自动接受差异来隐藏回归。没有执行的检查保留为未验证，不能仅凭新增文档核销覆盖项。
